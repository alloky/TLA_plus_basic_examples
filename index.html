Устройство TLA+/Pluscal — инварианты и граф состояний

Три кита модели: состояния, переходы и проверка инвариантов на всём графе

01

Состояния программы

Значения всех переменных в конкретный момент. Например: mutexA = FALSE, mutexB = TRUE, pc = "LockB"

02

Переходы между состояниями

Каждая строка кода — это действие (action), меняющее состояние. Граф состояний = все возможные пути выполнения.

03

Инварианты

Утверждения, которые должны быть истинны в любом состоянии. Например: "не более одного потока в критической секции".

Пример: Два мьютекса A и B, два потока. Thread1 берёт A→B, Thread2 берёт B→A. Классический deadlock философов — но с двумя мьютексами.

Как выглядит deadlock в графе состояний

⚠️

Что видит Model Checker

Error: Deadlock reached.

State (num = 3): mutexA = TRUE, mutexB = TRUE
Thread1: ждёт mutexB
Thread2: ждёт mutexA

Ни один процесс не может продвинуться.

TLC нашёл это за 0.03 секунды, перебрав 13 состояний.

Live Demo — код с deadlock

Thread1: A→B, Thread2: B→A. Классическое зацикливание.

Thread1 — берёт A, потом B

variables
  mutexA = FALSE;
  mutexB = FALSE;

process Thread1 = 1
begin
  LockA:
    await ~mutexA;
    mutexA := TRUE;
  LockB:
    await ~mutexB;
    mutexB := TRUE;
  Critical:
    mutexA := FALSE;
    mutexB := FALSE;
end process;

Thread2 — берёт B, потом A

process Thread2 = 2
begin
  LockB2:
    await ~mutexB;
    mutexB := TRUE;
  LockA2:
    await ~mutexA;
    mutexA := TRUE;
  Critical2:
    mutexB := FALSE;
    mutexA := FALSE;
end process;

Результат: TLC находит deadlock — оба потока заблокированы, каждый ждёт мьютекс, который держит другой.

Live Demo — код без deadlock

Оба потока берут мьютексы в одинаковом порядке: A→B. Иерархия ресурсов.

Thread1 — берёт A, потом B

variables
  mutexA = FALSE;
  mutexB = FALSE;

process Thread1 = 1
begin
  LockA:
    await ~mutexA;
    mutexA := TRUE;
  LockB:
    await ~mutexB;
    mutexB := TRUE;
  Critical:
    mutexA := FALSE;
    mutexB := FALSE;
end process;

Thread2 — тоже A→B

process Thread2 = 2
begin
  LockA2:
    await ~mutexA;
    mutexA := TRUE;
  LockB2:
    await ~mutexB;
    mutexB := TRUE;
  Critical2:
    mutexA := FALSE;
    mutexB := FALSE;
end process;

Результат: TLC проверяет все 12 состояний — deadlock не найден. Invariant Termination выполняется.

01

Почему Spec перед Build

Находим ошибки в логике до написания кода. Исправить спецификацию — 5 минут. Исправить баг в проде — часы простоя и репутационные потери.

02

Quality Gate как барьер

Model Checker запускается в CI/CD. Если invariant нарушен — билд не проходит. Так же как unit-тесты, но проверяют все состояния.

Реальная применимость TLA+ в сравнении с инструментами

  • • Race Detector (Go, TSAN): Проверяет, что в текущих запусках не было гонок. Если тест не покрыл конкретный interleaving — баг останется незамеченным.
  • • TLA+ / Model Checker: Проверяет, что во всех возможных запусках не будет гонок. Перебирает всё пространство состояний и гарантирует: если спецификация верна, багов нет.
  • • Аналогия: Race detector на стресс-тестах — как уронить телефон с 1 метра 100 раз и не увидеть на экране ни одной царапины. TLA+ — как вывести формулу прочности стекла телефона и предсказать, что с такой высоты он не поцарапается ни при одном падении.
